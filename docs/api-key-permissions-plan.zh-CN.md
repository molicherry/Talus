**API Key 权限编辑与旧版本迁移方案**

状态：已在 `feat/api-key-permission-edit` 分支实施。设计基于仓库 `cf5c7ac`，2026-10-23；验收用例登记在 `tests/coverage.json`。

目标是让管理员直接修改现有 Key 的操作权限和服务器范围，调用方继续使用原密钥；升级后旧 Key 也可进入同一编辑流程。权限迁移、密文迁移、所有者回填分别处理，避免互相覆盖数据。

**1. 已核实的项目现状**

- [APIKey 模型](../backend/internal/model/apikey.go)已经包含 `scopes`、`server_ids`、认证哈希、可选的加密明文、加密版本及所有者版本，没有权限更新版本号。
- [服务层](../backend/internal/service/apikey.go)只实现创建、列表、删除、查看密钥和验证。[仓储](../backend/internal/repository/apikey.go)按哈希查询数据库；[鉴权中间件](../backend/internal/server/middleware/auth.go)每次 HTTP 请求读取权限，没有权限正向缓存。
- [权限规则](../backend/internal/server/middleware/scope.go)把 Key 管理接口设为 JWT-only；这与“仅管理员”不是同一条件。当前 API Key 管理路由没有额外的管理员角色检查。新增接口必须显式加入规则表，因为未注册的路径目前默认放行。
- `server_ids` 为 NULL 或空列表表示全部服务器；非空列表表示指定服务器。这个约定需要保留，尤其不能把加载失败、未知选择或已删除服务器过滤成空列表。
- 创建时省略 `scopes` 使用当前默认值，显式 `[]` 被拒绝。更新不能复用省略即默认的创建语义。当前模型数据库默认包含 5 项，而服务层默认包含 `services:read` 在内的 6 项，实施时应统一未来新记录的默认值，不能重写旧记录。
- [启动代码](../backend/cmd/server/main.go)存在 `2026-09-24-services-read-scope` 一次性补权；[ApplyOnce](../backend/internal/repository/migrations.go)同时兼容旧 golang-migrate 的 `schema_migrations(version, dirty)` 和新迁移账本。
- [密文迁移](../backend/internal/repository/secret_migration.go)支持有密文的旧 Key，且保留仅有哈希的旧 Key；[所有者回填](../backend/internal/service/apikey_owner_backfill.go)只处理升级边界内的无主旧记录。
- [终端服务](../backend/internal/service/terminal.go)的持续会话撤销目前只覆盖 JWT。API Key 在握手时验证权限，随后不会因为数据库权限改变自动断开。

**2. 功能边界和管理权限**

权限编辑提供修改 `scopes` 和 `server_ids`、并发冲突提示、变更审计、旧 Key 自动纳入编辑，以及终端撤权。编辑权限时密钥 ID、明文、哈希和前缀保持不变，不要求调用方重新配置。另提供用户明确触发的密钥更换，见第 11 节。

建议将 API Key 管理统一为有效管理员 JWT 可用，包括创建、列表、编辑、删除和查看密钥。API Key 本身即使带历史 `*` 也不能管理任何 Key。服务层再次检查可信 Principal，避免仅靠前端按钮控制。管理员可以处理旧的无主 Key，编辑功能不等待后台所有者回填。

这是对现有“所有有效 JWT 可进入 Key 管理”的管理策略收紧，应在发布说明中说明；普通 JWT 返回 403。所有者字段本次继续用于归属和日志，不引入按用户分区的多租户权限模型。

服务器范围沿用当前含义：约束服务器及绑定服务器的服务；不把未绑定服务器的全局服务或凭据目录自动改造成服务器资源。界面说明应准确描述这一边界。`servers:exec` / `servers:terminal` 仍允许 SSH 账户本身能够执行的操作，取消文件 API 权限不会限制 shell 的文件操作能力。

**3. 接口与请求语义**

新增 `PATCH /api/v1/api-keys/{id}`，仅接受权限字段和并发版本：

```json
{
  "expected_revision": "3",
  "scopes": ["servers:read", "metrics:read", "services:read"],
  "server_ids": [12, 18]
}
```

| 字段 | 省略 | 显式值 | 非法值 |
| --- | --- | --- | --- |
| `expected_revision` | 400，必须携带 | 与当前 `permissions_revision` 相等才更新 | NULL、非正整数字符串、超出 PostgreSQL bigint 范围均拒绝 |
| `scopes` | 保留原值，不套用默认权限 | 非空列表完整替换；按当前允许的 scope 验证、去重并固定排序 | `null`、`[]`、未知 scope、`*` 均拒绝 |
| `server_ids` | 保留原值 | 非空列表完整替换；`[]` 明确表示全部服务器 | `null`、非正整数、无法访问或不存在的新增服务器 ID 均拒绝 |

至少提交一个权限字段。拒绝未知字段、错误类型、多个 JSON 文档及超限请求体，避免客户端误以为某项配置已更新。Go 请求解码必须区分“缺省 / null / 空数组”，单纯使用指针切片不能区分缺省与 null，应使用带存在标记的字段类型或原始 JSON 字段校验。

指定服务器列表中的历史已删除 ID 可以继续保留，但不能新增不存在的 ID。实现为：旧集合中的 ID 允许保留；新增集合中的 ID 必须存在。仅修改 scopes 时不校验或清理原服务器列表。旧列表即使只剩失效 ID，也仍表示一个受限集合。

成功返回 200 和更新后的安全元数据，继续使用项目的 `data` 包装：

```json
{
  "data": {
    "id": 7,
    "name": "monitoring",
    "key_prefix": "0123abcd",
    "scopes": ["metrics:read", "servers:read", "services:read"],
    "server_ids": [12, 18],
    "created_at": "2026-10-01T08:00:00Z",
    "permissions_revision": "4",
    "permissions_updated_at": "2026-10-23T02:00:00Z"
  }
}
```

不返回密钥明文。列表、创建结果也补充这两个元数据字段；revision 用十进制字符串传输，避免 JavaScript 整数精度问题。列表 DTO 将历史 NULL scopes 显示为 `[]`，不把它变成默认权限；数据库原值可以保留。

错误沿用现有 envelope：400 参数错误，401 登录失效，403 非管理员或 API Key 调用，404 Key 已删除，409 `api_key_revision_conflict`，503 数据库/事务审计不可用或提交状态待确认。版本不匹配时不自动重试覆盖。期望版本相同且有效权限集合完全一致时返回原数据，不增加 revision，也不触发会话撤销。

**4. 数据模型、原子更新与日志**

新增两列即可；权限数据格式本身没有改变，不另设一套永久的“旧 Key”表：

| 列 | 类型及初值 | 用途 |
| --- | --- | --- |
| `permissions_revision` | bigint，NOT NULL，DEFAULT 1，CHECK > 0 | 乐观并发控制及会话权限版本 |
| `permissions_updated_at` | timestamptz，可 NULL | 权限最近一次明确写入时间；旧记录初始化为 NULL，表示历史时间未知；新建记录写创建时刻 |

迁移完成状态记录在现有迁移账本。不要复用 `crypto_version` 或 `owner_binding_version`，三者含义不同。

写入流程：管理员校验 → 获取按 API Key ID 隔离的权限锁 → 开启事务并 `SELECT ... FOR UPDATE` → 检查 revision → 合并显式字段并验证 → 用列白名单更新权限、revision 和时间 → 同事务写安全审计 → 提交 → 标记该 Key 的旧终端会话失效 → 释放锁并返回结果。

仓储使用明确列集合，避免 GORM `Updates(struct)` 忽略空切片，也避免 `Save` 覆盖后台更新的 owner、密文和盐。JSONB 数组通过明确的序列化路径写入。删除与更新互斥，删除也接入相同会话撤销路径。

变更审计动作使用 `api_key.permissions.update`。事务内持久化操作者、目标 Key ID、修改前后 scopes/server_ids、前后 revision、操作 ID 和时间。详情使用固定结构和大小限制，记录的是校验后的权限数据，不保存请求原文、密钥、哈希、盐或密文。审计写入失败则本次修改回滚。

现有 usage capture 仍负责成功、拒绝、冲突和失败的操作摘要，不承担事务一致性。需要同步补充路由动作、后端过滤/报表动作列表、敏感动作保留策略、前端筛选和翻译；摘要保存修改前后的 revision，完整权限差异保存在事务审计。`usage/operation.go` 的 metadata/reason 白名单需要显式接纳这些字段及新冲突/终端关闭原因，否则日志会丢失它们。安全审计即使 usage capture 不可用也能生成独立 operation ID。

若数据库 COMMIT 返回结果不确定，不能声称“修改失败所以权限未变”：该 Key 暂停新的权限准入，通过主库锁定读取确认事务结果；前端提示刷新确认，不自动重提。已提交的撤权收尾不能依赖浏览器是否保持连接。这可以参考现有 [JWT gate](../backend/internal/gate/gate.go)的 pending fence 和恢复模式。

**5. 权限生效与已有连接**

| 场景 | 约定 |
| --- | --- |
| 新的 HTTP 请求 | 更新提交之后获得鉴权许可的请求读取新权限；缺 scope 或不在服务器范围返回 403 |
| 已获准的普通 HTTP 请求 | 允许原请求结束；已经发送的命令和已产生的远程副作用不能回滚 |
| 分片上传/续传 | 每个 status/chunk/complete 请求重新鉴权；恢复 token 不能绕过新 scope 或服务器限制 |
| API Key 终端 | 任何实际权限变化都结束该 Key 已建立及正在准备的终端；用户可以按新权限重新连接 |
| JWT 终端 | 不受某个 Key 的权限更新影响 |
| 已开始的单次下载、Exec、Relay | 遵循已获准请求规则；本次不承诺取消远端正在执行的工作 |

在当前单 Hub 部署前提下，新增 API Key 专用 gate 和会话 registry，按 `APIKeyID` 归类，不能把它放进以 UserID 为键的 JWT registry。普通请求的鉴权准入、终端注册/ready/输入准入与权限提交使用同一个 Key 锁，读权限仍来自主库。

终端持有 Key ID 和 admission revision；注册、ready 及每次 input/resize 前验证当前 revision，旧版本拒绝新的输入许可。锁只覆盖许可判定，不跨越可能阻塞的 SSH 写操作；提交之前已取得许可的写入属于在途操作。终端采用现有取消、强制关闭、有限清理预算和 `cleanup_pending` 机制，并返回可识别的 `api_key_permissions_changed` 关闭原因。

更新提交后，在释放 Key 锁前完成会话失效标记并禁止新的旧版本准入，随后异步/有界地关闭 WS 与 SSH 资源。资源清理慢不能恢复旧权限。未来若支持多 Hub，需要跨实例撤销通知或轮询及明确生效时限；本方案不把进程内 registry 描述成分布式保证。

**6. 旧版本 Key 的迁移矩阵**

| 旧数据形态 | 自动处理 | 升级后的行为 |
| --- | --- | --- |
| 已有正常 scopes/server_ids | 原样保留，补 revision=1，更新时间 NULL | 原 Key 继续认证，可编辑 |
| 数据库完全没有 scopes 列 | 在 AutoMigrate 前识别；写入冻结的兼容基线，见下文 | 保留原 Key，进入显式权限体系 |
| scopes 列存在，但某行 SQL NULL、JSON null 或 `[]` | 不填默认权限，读取按空集合处理 | 保持受 scope 控制的能力为空；管理员可明确授权 |
| scopes 有历史 `*` 或未知字符串 | 不批量扩权、删除或展开 | 未改 scopes 时保留；修改 scopes 时需明确替换为当前支持的具体权限 |
| 尚无 server_ids 列，或值为 NULL / `[]` | 按现有规则视为全部服务器 | 编辑时可切换为指定服务器 |
| 指定服务器已删除 | 保留 ID，不过滤成空数组 | 标注失效服务器，仍保持受限；管理员可保留、替换或明确选择全部 |
| 只有认证哈希，没有可恢复明文 | 不尝试恢复明文，不重生成 Key | 原调用方仍可认证和使用更新后的权限；查看明文继续返回不可用 |
| 有旧版加密明文 | 继续执行已有独立密文迁移 | 明文和认证哈希不变，之后可正常编辑权限 |
| 无 user_id 或 owner_binding_version=0 | 复用已有迁移边界和后台回填 | 不阻塞管理员编辑，权限更新不覆盖回填结果 |
| 非数组 JSON 或类型错误 | 预检报告对应记录 ID，阻止权限迁移完成 | 修复数据后重试，不猜测权限或悄悄转成全部访问 |

完全没有 scopes 列时，冻结的兼容基线采用当前项目升级路径的默认能力：`servers:read`、`servers:exec`、`servers:terminal`、`metrics:read`、`credentials:read`、`services:read`。它不是动态引用“当前全部权限”，不能随未来新增能力变化；不补发 `servers:write`、`services:relay` 或文件权限。

这类最早期无权限模型的 Key 不能保证保留当年的全部隐式访问；方案明确把它迁入上述兼容基线，管理员可以使用原 Key 补选所需能力。已经显式保存 `servers:write` 的早期 Key 则原样保留，不能因后来缩小默认集合而被移除。

已有 scopes 列但缺少旧 `services:read` 迁移标记时，无法仅凭数据判断它来自旧版隐式访问，还是管理员刻意不授予该权限。默认保留现存 scopes，输出需要检查的 Key 数量和 ID，由管理员明确补选；不能把“缺少迁移标记”当成自动授权依据。历史 `*` 在读取时仍按旧规则处理，但界面必须提示它包含未来 scope；主动替换后变成固定的具体权限集合。

**7. 启动迁移顺序与防止重复补权**

沿用项目的单 Hub、短维护窗口升级方式。停止旧 Hub 和事务后再执行迁移，不允许新旧程序混跑修改权限。

1. 保留数据库卷和原 master key，生成并验证可恢复备份。迁移预检读取列结构、已有账本和权限 JSON 类型，不输出密钥材料。
2. 继续执行现有所有者 schema 准备。在 AutoMigrate 之前运行 `PrepareAPIKeyPermissionsSchema`：使用事务、迁移 advisory lock 和有界锁等待；已存在 api_keys 时识别缺失列，初始化冻结基线或保留已有值，再增加 revision/更新时间列。已有表的数据、DDL 和本阶段标记在同事务提交；首次安装无表时交由新模型创建。
3. 执行 AutoMigrate。模型默认只影响未来记录。随后执行现有密文迁移，保留其独立的可恢复性与验证逻辑。
4. 完成权限迁移核验及旧补权退役：检查新字段、JSON 形态和账本；删除启动流程中旧的自动 `services:read` UPDATE。在同事务内登记新的权限迁移完成记录，并将旧 `2026-09-24-services-read-scope` 标记结清（若不存在则只登记，不执行补权）。新记录明确注明旧补权已退役，不能把登记解释为本次增加了 scope。
5. 迁移和核验成功之后才开放 HTTP；失败时停止启动，记录记录 ID/阶段，修复后重试。新的安全相关迁移不能沿用旧补权“报错但继续启动”的行为。后台所有者回填继续独立运行。

迁移账本应复用现有表结构识别与 fallback 逻辑，支持 `schema_migrations(version, dirty)`，不能直接假定存在 `id` 列。可提取 ApplyOnce 的事务/账本能力以记录多步迁移，不通过重复启动 SQL 实现默认权限同步。

明确禁止任何启动或后台任务把用户已经编辑过的 Key 重置为默认权限。验证“移除 services:read → 连续重启 → 权限仍缺失”，同时覆盖账本被恢复到旧备份时的情形：新的退役流程只结清标记，不重授权限。

**8. 前端交互与版本兼容**

在 Key 行新增“编辑权限”，抽出创建/编辑共用的 scope 与服务器选择器，但分开生成请求。编辑时用服务器返回的权限填充，不调用创建表单的默认重置逻辑。明确展示“保存后密钥不变”和终端连接会因权限变化结束。

保存只提交实际编辑的字段及打开表单时读取的 revision。指定服务器加载失败时保留当前选择，禁止提交一个无法确认的新服务器范围；不妨碍独立修改 scopes。全部服务器是一个明确选项，只有用户选择该选项时才发送 `server_ids: []`。

历史 wildcard、未知 scope、空 scopes 和已删除服务器显示独立提示。编辑服务器范围时可省略 scopes 保留旧值；主动修改 scopes 必须选择当前支持的非空集合，不能在渲染时静默剔除未知值。历史无明文 Key 的编辑入口照常可用，不依赖 reveal 成功。

409 保留用户草稿，提示数据已被其他管理员修改，提供加载最新配置后重新比较；404 提示 Key 已删除并刷新列表；400 定位字段；503 或网络结果不明提示刷新确认。成功后刷新 Key 列表和相关详情，清理错误状态。

旧前端可继续消费新增字段，已有创建接口省略 scopes 的行为保留。新前端读到缺少 `permissions_revision` 的旧后端时禁用编辑并提示升级后端，不能默认补成 1。后端列表 DTO 兼容旧 NULL scopes，前端同步支持新增元数据、错误原因和中英文文案。

**9. 验收要求**

| 类别 | 必须证明的结果 |
| --- | --- |
| 原 Key 不变 | 同一原始 Key 在更新前后认证成功；哈希/前缀/密文/盐不被权限更新改写；允许与拒绝的接口随配置变化 |
| 更新语义 | 省略、null、空列表各有约定结果；只改一维不影响另一维；未知 scope、错误 ID、重复项、无变更及非法字段覆盖 |
| 鉴权 | API Key（含 `*`）不能 PATCH；普通 JWT 403；管理员可操作旧无主 Key；真实路由覆盖检查包含新增 PATCH |
| 并发 | 两个相同 revision 的修改仅一个成功；更新/删除竞争不复活记录；owner 回填和密文迁移不被覆盖 |
| 审计与故障 | 审计失败整体回滚；提交响应丢失后可读回确认；数据库未知提交结果期间停止旧权限准入；日志无 secret |
| 迁移 | 当前、无 scopes 列、NULL/空/未知/wildcard、只有哈希、旧密文、无主等样本均覆盖；旧 schema_migrations 格式可用 |
| 幂等与恢复 | 迁移中断后重启完成；迁移重复执行无差异；编辑后重启不补回服务或文件权限；错误 JSON 明确阻止启动 |
| 服务器范围 | 全部→指定、指定→全部、已删除 ID、仅失效 ID、绑定服务器的服务过滤与 SFTP 权限均覆盖 |
| 终端与在途操作 | 已连接、正在 SSH 准备、ready 边界与 input/resize 竞争均覆盖；权限变化后旧 revision 不获新许可；不同 Key/JWT 不误断 |
| 前端 | 原值回显、失败保留草稿、冲突处理、服务器加载失败不扩权、旧后端禁用编辑、不可 reveal 的 Key 仍可编辑 |
| 完整升级 | 用旧 schema + 合成原始 Key 启动真实 Hub，完成迁移、PATCH、原 Key 请求、重启和撤权检查 |

迁移和并发测试使用真实 PostgreSQL；终端撤销使用已有本地 SSH/WS 测试设施验证实际停止输入和释放资源，不能只测版本常量。实施时将用例接入 `tests/coverage.json` 和相关 gate，由生成器更新 `tests/coverage.md`，不手工编辑生成报告。

**10. 实施拆分与发布**

| 阶段 | 主要改动 | 完成条件 |
| --- | --- | --- |
| A 数据与迁移 | model、repository、启动迁移编排，旧补权退役，迁移样本 | 旧 Key 可原样认证，重复启动不改变授权 |
| B 后端更新 | handler/service/repository、管理员管理策略、JWT-only 路由、revision 和事务审计 | 原 Key 更新权限及并发/失败路径验收通过 |
| C 持续连接 | API Key gate、独立会话 registry、终端准入/撤销、删除路径联动 | 无准备阶段和输入许可的撤权竞态 |
| D 前端与发布 | API/schema/hooks、共用表单、编辑与冲突 UI、日志动作/翻译、README 和完整升级测试 | 升级后可在页面修改旧 Key，原调用配置继续有效 |

可按阶段开发，但启用权限编辑应等待 A–D 共同验收，避免先发布编辑按钮却让旧终端继续使用已撤销权限。部署先停止旧 Hub，备份后启动新 Hub，检查迁移摘要，再用合成/专用验证 Key 检查保留密钥、缩权和重启行为。

回退首选关闭编辑入口或回退前端，同时保留新鉴权与迁移代码。纯权限列变更虽是增量 schema，也不能据此承诺旧程序的撤权与补权语义兼容。需要整版回退时，只能使用经过验证的兼容版本，或恢复升级前数据库与原 master key；后者会丢失升级后的变更并可能恢复旧权限。旧 Argon2id-only 程序仍受现有密文迁移的回退限制。

**11. 随机更换密钥值**

复制按钮旁提供“更换密钥”。确认弹窗说明旧值立即失效且原终端断开，确认后调用 `POST /api/v1/api-keys/{id}/rotate`，仅接受正整数十进制字符串 `expected_revision`。路由同时要求管理员 JWT、JWT-only scope 规则和敏感接口频率限制；服务层再次检查管理员身份。

使用与创建相同的 `crypto/rand` 生成 32 字节随机值，编码为 64 位十六进制字符串；重新生成盐、认证哈希、前缀及当前版本密文。事务行锁核验 revision 后，仅更新密钥材料和 revision，不改 ID、名称、创建时间、所有者、原始 scopes/server_ids（含 NULL、历史未知 scope 和失效服务器 ID）以及权限更新时间。仅有哈希的旧 Key 无需知道旧明文也可更换；新值可以正常查看、复制。

`permissions_revision` 同时作为密钥材料和权限的准入版本：任何一项变化都递增，避免权限编辑、更换和删除互相覆盖。更换审计使用 `api_key.rotate`，与密钥更新同事务持久化，仅记录前后版本及操作者/资源，不记录密钥材料。鉴权在准入锁内重读新版本后还必须核对哈希，防止旧哈希已查到、但更换已经提交的请求被误准入。已获准的普通请求可结束。

成功响应以 `Cache-Control: no-store` 返回新密钥和安全元数据，并结束该 Key 正在准备或已建立的终端，其他 Key/JWT 会话保持有效。审计失败回滚，不返回候选密钥；提交结果不确定则维持准入隔离并后台恢复，前端要求刷新确认，不自动重试。409 同样要求刷新版本。前端仅在结果弹窗显示新值，提供复制按钮，不把明文写入列表缓存；关闭弹窗后仍可通过原有复制入口取得当前值。

验收包括真实 PostgreSQL 事务、并发更换只有一个成功、旧密钥查找与更换交错、提交结果丢失/回滚/未决、真实 HTTP/WS/SSH 终端撤销、服务重启后的新密钥认证，以及桌面/移动端确认、复制和异常刷新流程。
